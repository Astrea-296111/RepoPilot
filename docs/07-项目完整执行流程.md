# 07｜把重复邮箱 Demo 完整走一遍

先在 `examples/demo_repo` 跑 `python -m pytest -q`，实际结果：`1 failed`，堆栈指向 `app/users.py` 抛出 `ValueError: UNIQUE constraint failed: users.email`；测试期待 `DuplicateEmailError`。为什么先证明失败？否则「修复后通过」可能只是一个原本就通过的测试。

`eval/run_eval.py` 每次将 Demo 复制到临时目录，创建基线 Git commit，再启动 FakeLLM。它预设的模型输出序列固定，所以能稳定测试工具、上下文、状态和验证逻辑；不衡量真实 LLM 的修复能力。实际运行记录如下（时间随机器变化）：

```text
baseline: python -m pytest -q -> exit 1, 1 failed
planner: goal=修复重复邮箱错误, test_command=python -m pytest -q
step 1: read_file app/users.py -> 看到 raise ValueError(...)
step 2: run_command python -m pytest -q -> exit 1
        observation: test_duplicate_email FAILED / ValueError
step 3: apply_patch app/users.py -> 改为 raise DuplicateEmailError(email)
step 4: run_command python -m pytest -q -> exit 0, 1 passed
step 5: git_diff -> 看到一行异常映射改动
step 6: final -> 程序再次 run_command（exit 0）并取 git_diff
final: status=completed, changed_files=[app/users.py]
```

本次 `python eval/run_eval.py` 输出 `task_success: true`、基线 exit 1、修复后 exit 0、`steps: 6`、`tool_calls: 7`，一次运行耗时 1.342 秒，Token 计数为 0（FakeLLM 没有 provider usage）。最后两次工具调用是程序侧的最终测试与 Diff，所以 6 步和 7 次工具调用并不矛盾。

要自己复现，用 README 的临时目录副本命令；也可以先直接读源码：`agent.py:demo_responses` 给 FakeLLM 的脚本，`agent.py:run` 负责执行，`test_core.py:test_agent_loop_demo_end_to_end` 检查失败基线、通过复测和 Diff。会话 JSON 在副本的 `.repopilot/sessions/`；`repopilot sessions /tmp/repopilot-demo` 找 ID，`repopilot show ID --repo /tmp/repopilot-demo` 看每步 `tool_history`。

这里「Reflection」不是隐藏的第二个 Agent：当测试失败，程序把测试输出作为 Observation 传回同一循环；下次模型看到失败再决定修补。FakeLLM 下一步早已写死，真实模型的反思质量需要单独测。工具测试通过也不能证明真实任务完成；目标仓库有未覆盖的行为还需要人审。

### 这一章你面试时应该能说什么

「我先确认测试失败，再在临时 Git 副本上跑脚本化 Agent：读取、复现、精确替换、复测、Diff、最终程序侧复验。基线 1 failed、结果 1 passed。它验证 harness，不是模型能力基准。」
