# 11｜简历与项目介绍：按验证程度选择说法

## A. 30 秒项目介绍

「我做了一个 Python Coding Agent：输入仓库和修复需求，它先用 AST 做 Repo Map 和可解释 Top-K 检索，再让模型生成计划，并在显式 Agent Loop 中按 JSON 协议逐步读文件、改代码和跑测试。程序负责 Pydantic 校验、审批、路径边界、超时、循环停止和最终复验。为了不只靠 Demo，我又做了 Mini Benchmark：每个任务先确认基线失败，Agent 完成后禁止修改受保护测试，再注入 hidden regression tests 独立复测。当前用 Qwen3.8-Max 在 5 个独立 Python Bug 任务上每题跑 1 次，5/5 首轮通过；这个结果只代表当前小任务集，不当作通用成功率。」  

## B. 2 分钟项目介绍

「我希望理解 Coding Agent 为什么不是一次模型调用。大型仓库不能全部塞入上下文，所以我用 Python AST 抽取类、函数、签名和 import 生成 Repo Map，再按文件名、符号和文本词频选 Top-K。Planner 给出目标、步骤和测试命令；Agent 是一个有 max_steps 的 while 循环，每轮构造有限上下文，模型返回 JSON 工具调用或 final，Pydantic 校验后由 Python 执行工具并记录 Observation。工具输出会截断，近期历史保留、旧历史压缩；重复三次相同工具调用停止。模型说 final 也不能直接相信，程序会重新运行计划测试，失败继续循环，成功后才取 Git Diff。

安全方面，文件工具限制仓库边界和敏感路径，写文件/命令支持 approval；默认提供限资源、禁网的 DockerExecutor，也可在可信仓库显式选择 local。会话逐步保存成 JSON，支持 CLI、resume 和简单 FastAPI。

评测方面，我把最初的单一 FakeLLM Demo 扩成 Mini Benchmark v2：5 个故意带 Bug 的独立 Python 仓库，覆盖异常处理、分页边界、配置优先级、路径安全和状态修改。每题先验证基线确实失败，Agent 运行时只拿到仓库和任务描述；结束后检查测试目录没有被改，再注入 hidden regression tests。GitHub Actions 当前 Qwen3.8-Max 每题 1 次实测 5/5，median steps=3、tool calls=4、tokens=3554、duration=27.205s。样本仍然很小，下一步是扩到 20–30 个任务、每题 3 次并加入 one-shot baseline。」  

## C. 当前可用于简历的项目描述

- 独立实现 Python Coding Agent 的 Planner、显式 Agent Loop 与 JSON/Pydantic 工具协议，支持测试失败 Observation 回灌、JSON repair、`max_steps`、重复调用停止和程序侧最终测试复验。
- 使用 Python AST 构建 Repo Map，结合文件名、代码符号与文本词频进行 Top-K 检索，并通过 Tool Output Truncation、旧历史摘要和 Context Budget 控制长任务上下文增长。
- 实现仓库路径防越界、Approval、限时 Local/Docker 执行、JSON Session、CLI 与 FastAPI；构建 5 任务 Mini Benchmark，引入 protected tests 与 hidden regression tests，Qwen3.8-Max 当前每任务 1 次实测 **5/5 首轮通过**，并记录步骤、工具调用、Token 与耗时。

## 指标怎么写才不会过度宣传

| 指标 | 当前证据 | 可以怎么说 |
| --- | --- | --- |
| 项目自动测试 | GitHub Actions：`21 passed` | 可写「21 项自动测试通过」 |
| Mini Benchmark | 5 个独立 Python Bug 任务，每题 1 次 | 明确写「自建 5 任务 Mini Benchmark」 |
| Qwen3.8-Max | 2026-09-29 Actions：5/5 first-run resolved | 可写「当前 5 个任务首轮 5/5」，不要写「通用成功率 100%」 |
| 中位步骤/工具调用 | 3 steps / 4 tool calls | 可作为评测数据 |
| 中位 Token/耗时 | 3554 tokens / 27.205s | 必须注明是当前 5 个任务的中位数 |
| Docker runtime 与 Compose | 仍未在本次 Windows benchmark 中验证 | 不写「生产部署已验证」 |
| SWE-bench | 未跑 | 不写 SWE-bench 成绩 |

## 为什么 5/5 仍不能叫“成功率 100%”

任务量只有 5 个，且都是为 V2 Harness 准备的小型 Python Bug；每题也只运行 1 次。它能证明真实模型的端到端闭环已经跑通，并能比较不同任务的步骤、Token 和耗时，但不能代表任意真实仓库。要形成更可靠的指标，需要扩大到 20–30 个任务、每题至少 3 次，并加入同模型 one-shot baseline。

## 一个值得在面试里讲的评测器问题

第一次 5 任务真实运行得到 4/5。失败的 duplicate-email hidden test 要求异常消息必须包含邮箱地址，但公开任务只要求「抛出 DuplicateEmailError，并保持正常注册行为」，所以 hidden test 偷加了未声明规格。这个问题随后被修正；同时把 benchmark 的退出语义改成：模型 miss 记录为评测结果，只有 runner/baseline 等基础设施错误才让真实 benchmark job 失败。脚本化 sanity check 使用 `--require-all`，用于确保评测器自身始终能判定已知正确修复。

这个案例可以用来回答：「你如何避免 evaluator 把合理 patch 误判为失败？」
