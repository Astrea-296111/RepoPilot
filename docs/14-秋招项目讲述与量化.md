# RepoPilot 秋招项目讲述与量化

> 更新：2026-09-30 已完成 3 个项目、10 个历史 Bug、60 次真实模型对照。最新数据见 [外部实测报告](17-外部历史Bug实测结果.md)，完整简历与 STAR 见 [项目讲述](16-项目STAR与简历.md)。本文保留前期开发集实验的推理过程，不能与新任务结果合并。

## 30 秒项目介绍

RepoPilot 是一个面向 Git 仓库中小型 Python Bug 的 Coding Agent：先通过 AST 建立仓库地图并选取相关文件，再由 Qwen3.8-Max 规划和逐步调用读文件、搜索、改代码、跑测试等工具；程序校验结构化动作、记录轨迹，并在结束时重新运行测试。CLI、API、会话恢复和 Windows Actions 评测让过程可以复现。它是一个可解释的工程原型，不是通用自动修复产品。

## 面试中最有说服力的技术故事

1. **问题**：自建四道共享 helper 题的定向实测中，Agent 3/4，词法 Top-K one-shot 0/4。逐题轨迹表明 one-shot 生成的 `old_text` 与文件不匹配；它的输入缺少实际共享实现。
2. **假设与对照**：保持 Qwen 模型配置不变，把全部公开 Python 文件原文交给一次调用。四题 one-shot 得到 4/4；这否定了“此前四题证明多步 Agent 更强”的讲法。每题只有一次运行，不能声称稳定提升。
3. **工程改进**：为相对导入保留 AST 层级，用同仓库模块图补充 Top-K 的直接依赖。完全无词法命中时，依据非测试源码的导入次数选择共享实现。保留原词法与完整上下文模式，用 `graph` 单独做消融。
4. **离线量化**：用 25 题的已知脚本化补丁路径作参照，Top-K 命中全部参考修复文件的任务数从 20/25 到 25/25；平均源码原文从 409.7 增至 440.2 字符，平均文件数从 2.16 增至 2.36。这是开发集上的文件召回指标，**不是**修复成功率、token 节省或跨仓库泛化率。
5. **真实模型验证**：[五题导入图 one-shot 运行](https://github.com/Astrea-296111/RepoPilot/actions/runs/36574356369)为 5/5，中位 1096 tokens、8.641 秒模型调用耗时；[同五题 Agent 运行](https://github.com/Astrea-296111/RepoPilot/actions/runs/36575414927)为 5/5，中位 6 步、7 次工具调用、12002 tokens、73.558 秒总耗时。每题只跑一次，不能声称稳定优劣。Agent 两题曾改公开测试；评分前恢复并通过隐藏测试，但按无测试改动口径为 3/5，one-shot 为 5/5。

| 代价 | 逐任务模型 total tokens、模型调用耗时的中位数；Agent 另记 steps / tool calls | 每次 Actions 的 `oneshot-qwen-shard-*` / `agent-qwen-shard-*` JSON artifact |
| 失败归因 | 将超时、传输、协议、精确补丁、行为错误和 Agent 步数上限分开 | 逐任务 `failure_category` 与模型响应 / hidden test 输出 |

要做可比实验，固定任务、模型版本与地域、推理力度、流式配置、超时和每题运行次数；`eval/merge_shards.py` 检查分片完整性，`eval/compare_results.py` 拒绝未配对的分母。早期和定向运行不要拼成一个总成功率。自建 25 题规模小且主要是微型仓库，隐藏测试在同一 Actions runner 上，尚未形成严格的对抗隔离。

## 简历写法示例

> RepoPilot｜Coding Agent 与评测系统：实现 AST 仓库地图、结构化工具循环、测试复验和可恢复会话；构建 25 题脚本化回归与 Qwen3.8-Max Actions 实测，记录逐题修复、调用、token、耗时及失败归因。定位 Top-K 漏检共享 helper，加入导入图补全；在自建 25 题的已知修复路径上，Hit@4 从 20/25 到 25/25，平均输入源码仅增加 30.5 字符。

这段应以自己确实能演示、解释和复现的贡献为准调整。不要写“修复率提升 25%”“比 Codex 更强”或“SWE-bench 25/25”：这三项均没有相应证据。

## 面试追问准备

- **为什么需要 Agent Loop？** 多轮可以在错误或上下文不足时补查、执行和复验；但在小仓库且完整源码可放进上下文时，单次调用可能更省时和 token。用相同条件对照判断何时值得付出交互成本。
- **为什么用精确补丁？** 它能阻止模糊覆盖；副作用是 `old_text` 缺失或重复会失败。检查原文是否在输入、定位失败类别，不把 patch 失败都归罪于模型推理。
- **Hit@4 为何不能当成功率？** 参考修复文件不是唯一解，选中文件也不保证模型正确修改；应同时看真实模型的隐藏测试通过率、成本与失败轨迹。
- **还缺什么？** 已补充三个独立项目的 10 个历史 Bug、三次重复与单次基线，完成运行期测试保护和独立评分。当前应优先改进重复动作与终止策略，使用新独立 Bug、完整仓库集成和更严格上下文消融验证；API 认证、持久化任务索引与更大仓库索引仍待完善。

公开面经中确实出现个人贡献、评测集构建与指标、Coding Agent 与现成产品的差异、上下文压缩等追问；可参考[这份整理](https://www.nowcoder.com/discuss/922659486983036928)。评测中记录轨迹、结果与代价，并用可运行的参考答案检查 grader，参考 [Anthropic 的 Agent eval 实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。
