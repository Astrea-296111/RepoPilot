# RepoPilot：项目 STAR、简历条目与面试讲述

## 项目定位与个人贡献

RepoPilot 是面向 Python 仓库 Bug 修复的 Coding Agent 与可复现评测系统。**我独立负责需求分析、架构设计、核心实现、用例构建、GitHub Actions 实测、失败分析与迭代。** 项目的价值在于把仓库理解、可控执行和可核查的修复结果串成闭环，并通过对照判断多轮 Agent 的收益与代价。

本稿依据截至 2026-09-30 的真实代码和运行记录。正式外部结果见 [测试报告](17-外部历史Bug实测结果.md)，原始数据见 [证据目录](../eval/evidence/2026-09-30)。

技术：Python、AST、Pydantic、Qwen3.8-Max、Docker、FastAPI、GitHub Actions

- **修复闭环：** 独立实现“仓库定位—规划—工具执行—测试反馈—最终复验”流程，封装读文件、搜索、精确补丁、写文件、执行命令和 diff 共 6 类工具；通过 Pydantic 校验动作、唯一匹配补丁和步骤/重复限制控制执行，逐步保存会话以支持恢复与问题追踪。
- **仓库上下文：** 针对词法检索漏掉共享 helper 的问题，构建 AST 符号地图与相对导入图补全；在自建 25 题开发集上，参考修复文件 Hit@4 从 20/25 提高到 25/25，平均输入源码仅增加 30.5 字符；使用 AST 实现片段补充大文件后部代码。

## STAR 完整讲述

**S｜背景：** 我想做一个能验证代码修改的仓库修复 Agent。实际难点有两个：相关实现经常散在共享模块里，给模型几个命中文件可能漏掉根因；即使模型生成了补丁，也需要执行测试才能判断是否修好，失败后还需要继续查找。

**T｜目标：** 我独立负责整个项目，希望用户输入仓库和问题后，系统能定位代码、执行修复并复验；同时，每次决策和测试都可以追踪。我还要回答一个工程问题：在什么情况下，多轮 Agent 值得比单次模型调用付出更多成本。

**A｜行动：** 我先用 Python AST 建立函数、类和导入关系的 repo map，通过词法匹配选择初始文件。定向测试发现单次调用生成的补丁旧文本不存在，我没有直接归因于模型能力，而是保持模型配置，用完整公开源码做对照；四题单次调用从 0/4 变成 4/4，说明之前的差异与上下文缺失有关。于是我加入相对导入图，补充共享实现；开发集 25 题的参考修复文件 Hit@4 从 20/25 到 25/25，平均只增加 30.5 个源码字符。

执行层我选择显式的规划与工具循环，便于直接检查每次状态变化。模型只产生 Pydantic 校验的 JSON，Python 执行 6 类工具；补丁要求旧文本唯一匹配，避免模糊覆盖。测试失败作为下一轮观察，结束前由程序再次执行测试；同时保存每步会话，并设置步骤和重复动作限制。

早期实测还发现 Agent 会改公开测试。我把这个问题落实成文件工具写保护和 Docker 只读测试挂载，再用全新的工作副本注入隐藏测试评分。为检验开发集之外的表现，我固定 3 个开源项目的 10 个真实历史 Bug，先确认旧版本失败、上游修复通过，再用 Qwen3.8-Max 对 Agent 和单次补丁各做 3 次重复，记录配对结果、token、耗时和失败轨迹。

**R｜结果：** 我完成了 CLI、API、可恢复会话、受约束的工具执行和可复现评测。正式 60 次试验中，Agent 补丁评分通过 25/30，其中正常结束且通过 23/30；单次基线通过 28/30。这个结果没有证明 Agent 更强，却帮助我定位了重复读取、已经修好仍重复跑测试，以及忽略兼容性边界的问题。我的判断是：当前任务中，单次调用已经足够强，后续应优先改进信息获取与终止策略，再用固定任务验证收益，而不是继续堆工具或增加循环。

## 30 秒项目介绍

我独立做了 RepoPilot，一个能读 Python 仓库、改代码并实际跑测试的 Agent。核心是 AST 仓库地图和导入图检索、结构化工具循环，以及固定测试的隔离评分。我先通过对照发现共享代码漏检，再改进检索；随后完成 3 个开源项目、10 个历史 Bug、60 次真实模型试验。项目让我能用代码和轨迹解释修复结果，也能明确多轮 Agent 在成功率、耗时和 token 上的取舍。

## 故事里的关键转折

最值得讲的是“如何发现自己的原始假设不成立”。早期 Agent 胜过 Top-K 单次调用，但补齐公开源码后单次调用也能成功，说明不能把检索差异包装成 Agent 优势。随后固定外部任务再次对照，单次基线仍更强。这个过程体现的是定位问题、控制变量、落实保护和评估取舍的能力；数字与技术选择都有证据。

## 技术决策说明

| 遇到的问题 | 使用的技术 | 选择原因 | 验证方式 |
|---|---|---|---|
| 仓库源码多，相关实现散在共享模块 | AST repo map、词法检索、相对 import 图补全 | 符号和导入关系可以直接提供解释和依赖路径，扫描不执行源码 | 开发集文件 Hit@4、同模型上下文对照 |
| 大模块的修复函数位于文件后部 | 按公开任务符号选取 AST 实现片段，保留可定位的行区间 | 文件头截断容易漏掉真正实现，按函数/类片段分配字符预算 | 上游完整模块任务、补丁与隐藏评分 |
| 单次生成无法利用执行失败继续修复 | 显式 Planner / Tool / Observation 循环 | 将模型决策与程序执行分开，失败输出进入下一轮，结束前实际复验 | 单次补丁基线、逐步轨迹、步骤上限 |
| 模型输出格式错误或模糊覆盖代码 | Pydantic JSON 协议、唯一精确补丁、原子写入 | 无效动作可拒绝；旧文本必须唯一匹配，降低误改范围 | 协议/补丁失败分类、单元测试 |
| 对话增长占满上下文 | 字符预算、近期观察保留、早期动作摘要 | 保留当前错误与任务要求，给长循环设置明确上限 | 上下文单测、失败轨迹；未测 token 压缩提升 |
| Agent 会话中改测试，导致结果难判断 | 文件工具写保护、Docker 只读测试挂载、干净 checkout 隐藏评分 | 用固定测试验代码，原始测试和评分器不接受模型改动 | 先验上游参考修复、受保护写入测试、grader 原始输出 |
| 中断后难重现，实测只看最终通过 | 每步原子保存 JSON 会话、工具日志、token/耗时/失败类型、GitHub Actions artifact | 将决策、代码改动和最终评分对应起来，定位失效环节 | 会话恢复测试、配对分片检查、可核查运行链接 |

## 面试追问边界

- 这是单 Agent 的规划与执行循环；没有实现多 Agent 协作或强化学习训练。
- 当前检索是词法、AST 与导入关系；没有用向量数据库，不能写成向量 RAG。
- 上下文预算按字符计算；不能写成精确 token 预算或量化压缩率。
- 会话恢复已实现，API 任务索引仍在内存中；不能称生产级分布式调度系统。
- 命令测试在 Docker 中禁网并限制资源；没有完成恶意代码攻防验证，不能保证绝对安全。
- 外部评测使用完整目标模块及所需包内导入的固定快照，不包含完整上游仓库。不是 SWE-bench。
- 60 次试验由 10 个 Bug 重复得到；不能说成 60 个独立 Bug。

## 常见追问与可回答的证据

**为什么没有使用向量数据库？** 当前任务先依赖精确符号、文件名和相对导入关系，这些结构能直接解释检索路径，AST 扫描也不执行源码。开发集证明导入图有用；是否加入向量检索，要在更大、多样化任务上对照，而不是为了技术栈更长。

**为什么显式写 Agent Loop？** 项目目标包括观察状态、工具协议和失败过程，显式循环便于控制和审计。它允许根据新证据继续修复，但当前对照没有证明这份策略优于单次调用。

**为什么选择精确补丁？** 可以限制修改范围，旧文本不唯一就拒绝写入。代价是模型必须看到正确原文；本轮单次基线的两次失败正是旧文本匹配失败，后续可评估带行区间的补丁协议，但当前尚未实现。

**为什么公开测试通过还需要隐藏测试？** 公开复现只证明原 Bug 被触发或消除，隐藏用例补充参数边界与旧行为兼容性。本轮大写十六进制任务中，直接修改全局正则通过了公开测试，却破坏旧解码模式，正是隐藏测试发现的问题。

**如果基线更好，项目有什么价值？** 我实现了可执行、可恢复、可评分的系统，并用对照知道它的当前边界。下一步是改善重复动作后的决策和成功后的终止；只有同条件结果支持，才主张更高修复率。完整失败样例见 [结果报告](17-外部历史Bug实测结果.md)。

**能不能证明大仓库通用修复？** 不能。当前是三个项目的目标模块与必要导入快照，只有 10 个独立 Bug；还需新任务、完整仓库集成、依赖安装和资源预算验证。
